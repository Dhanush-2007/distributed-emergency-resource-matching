# Local Kubernetes Deployment (Stage 9)

This guide documents the full local Kubernetes deployment for the Distributed Emergency Resource Matching System on Minikube.

---

## 1. Prerequisites & Resource Budget

### Prerequisites
- Docker (Docker Desktop)
- Minikube (`v1.30+`)
- `kubectl`
- Python 3.11 with project virtual environment (`.venv`)

### Resource & Memory Budget
- **Workloads at rest (11 pods)**:
  - 6 Storage Node StatefulSets (`ems-s0-a` through `ems-s2-b`)
  - 1 RabbitMQ StatefulSet (`rabbitmq-0`)
  - 1 Coordinator Deployment (`coordinator`)
  - 3 Domain Service Deployments (`request-service`, `resource-service`, `matching-service`)
- **Workloads when scaled (13 pods)**:
  - Up to 3 Matching Service replicas during high demand.
- **Resource Allocation**:
  - Minimum Memory: **4096 MB** (`minikube start --memory=4096 --cpus=2`)
  - Recommended Memory: **6144 MB** (`minikube start --memory=6144 --cpus=4`)
  - Python microservices requests: 100m CPU, 128Mi RAM (limits 250m CPU, 256Mi RAM).
  - Storage nodes requests: 50m CPU, 64Mi RAM (limits 200m CPU, 128Mi RAM).
  - RabbitMQ requests: 100m CPU, 256Mi RAM (limits 500m CPU, 512Mi RAM).

---

## 2. Deployment Order

Manifests must be applied in the following strict dependency sequence:
1. `k8s/00-namespace.yaml`: Creates the `ems` namespace.
2. `k8s/01-config.yaml`: Installs `ems-config` ConfigMap with cluster endpoints, sharding, and thresholds.
3. `k8s/02-secret.yaml`: Installs `ems-secret` Secret with broker credentials.
4. `k8s/rabbitmq.yaml`: RabbitMQ StatefulSet, headless service, ClusterIP, and NodePort.
5. `k8s/storage-nodes.yaml`: 6 storage StatefulSets and 6 headless services generated by `generate_storage.py --all`.
6. `k8s/coordinator.yaml`: Coordinator Deployment (`Recreate` strategy) and PersistentVolumeClaim for shard state.
7. `k8s/services.yaml`: Request Service, Resource Service, and Matching Service Deployments and Services.

## 3. Automation Scripts

### Start Cluster and Stack
```bash
./scripts/k8s_up.sh
```
Builds all five service images, loads them into Minikube, generates storage manifests, applies all resources in order, waits for rollouts, and verifies that all three shards report `HEALTHY`.

### Manage Port-Forwards
```bash
# Start background port-forwards (8000, 8001, 8002, 15672)
./scripts/k8s_ports.sh

# Terminate port-forwards
./scripts/k8s_ports.sh --stop
```

### Reset State
```bash
./scripts/reset.sh k8s
```
Tears down the namespace and PVCs, redeploys the stack, purges RabbitMQ queues, and seeds deterministic demo resources (`seed.py --fixed`).

### Teardown
```bash
# Complete teardown including PVCs:
./scripts/k8s_down.sh

# Teardown workloads while retaining persistent volumes:
./scripts/k8s_down.sh --keep-data
```

## 4. Service Access: NodePort vs Port-Forwarding

### Option A: Port-Forwarding (Recommended for Local Dev)
Run `./scripts/k8s_ports.sh` to forward localhost ports:
- Coordinator Diagnostics: `http://localhost:8000`
- Request Service API: `http://localhost:8001`
- Resource Service API: `http://localhost:8002`
- RabbitMQ Management UI: `http://localhost:15672` (Credentials: `ems` / `ems-dev-password`)

### Option B: NodePort Services
Minikube exposes dedicated NodePort services directly on the Minikube IP (`minikube ip`):
- Coordinator NodePort: `30080` (`http://$(minikube ip):30080/diagnostics/shards`)
- Request Service NodePort: `30081` (`http://$(minikube ip):30081/requests`)
- Resource Service NodePort: `30082` (`http://$(minikube ip):30082/resources`)
- RabbitMQ UI NodePort: `31672` (`http://$(minikube ip):31672`)

Alternatively:
```bash
minikube service -n ems request-service-nodeport --url
```

## 5. Verification & Testing

Run the automated Stage 9 Kubernetes verification suite:
```bash
.venv/bin/python scripts/k8s_verify_stage9.py
```
This runs 8 comprehensive verification drills:
1. Workload readiness and shard health check.
2. Inter-service DNS resolution and end-to-end matching.
3. Shard key distribution across all three storage shards.
4. Application pod self-healing during deletion under request traffic.
5. Matching Service scale-out to 3 replicas without duplicate assignment.
6. Storage node failover under sustained load and recovery upon return.
7. PVC data persistence across replica, coordinator, and RabbitMQ restarts.
8. RabbitMQ outage handling and sweeper recovery.

## 6. Troubleshooting

- **RabbitMQ Startup**: RabbitMQ relies on the `rabbitmq-data` PVC mounted at `/var/lib/rabbitmq`. The pod runs with `runAsUser: 999` and `fsGroup: 999`. If the broker enters CrashLoop, check `kubectl -n ems logs rabbitmq-0` and verify PVC mount permissions.
- **Probe Failures**: Storage nodes use `/health/live` and `/health/ready` on port 9000. Storage nodes will report unready (`503`) until they register with the coordinator and sync their initial state. A `startupProbe` is configured to prevent premature pod restarts during catchup.
- **DNS Resolution**: Storage nodes advertise their headless service DNS names (`ems-sX-Y-0.ems-sX-Y.ems.svc.cluster.local`). The headless services require `publishNotReadyAddresses: true` so other nodes and the coordinator can resolve node addresses even while the pod is catching up.
- **ImagePullBackOff**: Ensure `make images` succeeded and `minikube image load ems/<image>:1.0` was executed. All manifests use `imagePullPolicy: IfNotPresent`.
